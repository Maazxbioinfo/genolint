# GL005 — Contig naming mismatch within a script (`chr20` vs `20`)

## What it catches

Genome references come in two common contig-naming conventions: with a
`chr` prefix (`chr20`, `chrX`, `chrM` — UCSC-style) and without one (`20`,
`X`, `MT` — Ensembl/NCBI-style). Different tools and reference downloads
in the same pipeline can default to different conventions, and it's easy
to end up with a script that uses `chr20` in one command (e.g. a region
argument on `bcftools view -r`) and plain `20` in another (e.g. a
`samtools view` region, or a different tool's `-L`/regions argument)
without anyone noticing, because both are "valid" region strings on
their own.

GL005 flags a script where contig names appear in both conventions across
its commands:

```bash
# Flagged: same script, two different contig-naming conventions
bcftools view -r chr20:1-1000000 input.vcf.gz -o subset.vcf.gz
samtools view -b aligned.bam 20 > chr20.bam
```

## Why it matters

If the underlying reference/index actually uses one convention, a region
string in the *other* convention typically returns zero records/reads
rather than raising an error — a silent no-op that looks like a
successful run producing an (incorrectly) empty or partial result. This
is a common, hard-to-spot cause of "why is this output empty" bugs in
genomics pipelines, especially when a script mixes tools or was
assembled by copy-pasting commands from different sources/tutorials.

## The fix

Pick one convention for the whole script/pipeline and use it
consistently — usually whichever convention matches your actual reference
FASTA/index. If you need to interoperate with tools or files that use the
other convention, do an explicit renaming/liftover step (many tools ship
`chr`-prefix conversion utilities, or a simple sed-based contig rename on
a header) rather than mixing raw contig strings across commands.

## When to ignore it

- If the script intentionally operates on two different references with
  genuinely different naming conventions (e.g. one command targets a
  UCSC-style reference and another targets an Ensembl-style one, and
  that's correct for your workflow), this is a safe finding to dismiss.
- If the "contig" GL005 flagged isn't actually a contig — e.g. a sample
  name or file path that happens to look like `chr20`/`20` — that would
  be a false positive worth reporting rather than silently ignoring,
  since it points at an extraction gap.
