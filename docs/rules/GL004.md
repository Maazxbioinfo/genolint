# GL004 — SnpSift `has` with a substring instead of a full term

## What it catches

SnpSift's `has` expression checks whether an annotation field contains a
given value, e.g.:

```bash
SnpSift filter "(ANN[*].EFFECT has 'missense_variant')" input.vcf
```

`has` does a substring/containment check, not an exact term match. This
becomes a problem when the value you're checking for is itself a
substring of a *different*, unrelated term in the same field's vocabulary.
For example, `missense_variant` is a substring of
`missense_variant&splice_region_variant` (SnpEff's combined-effect
notation), so a `has 'missense_variant'` check will also match records
whose true annotation is that combined term — which may or may not be
what you intended, but is easy to get wrong silently. More subtly, some
SnpEff/ANN vocabularies have genuinely distinct terms where one string is
a plain substring of another with no delimiter at all (not just the
`&`-joined combined effects case), so `has` can match a term you never
meant to include.

GL004 flags a `has` check against a value that's a known substring of
other distinct terms in the relevant vocabulary, where a full/exact-term
match was more likely intended.

## Why it matters

Filtering on the wrong set of variants because of a substring match is a
correctness bug that's invisible in the command itself — you have to know
the annotation vocabulary to see it. It silently over- or under-includes
records rather than erroring, which is exactly the kind of mistake worth
a linter's attention.

## The fix

Use SnpSift's exact-match / set-membership constructs instead of `has`
when you mean "equals one of these exact terms," for example matching
against the full field value or using a construct that anchors the term
boundary rather than doing free substring containment. In practice:
double-check whether you want *exactly* `missense_variant`, or whether
you're fine catching combined-effect annotations too — and if you want
exactly one, use an exact-match check rather than `has`.

## When to ignore it

- If you genuinely want the broader match — e.g. you *do* want to catch
  `missense_variant` whether it appears alone or combined with another
  effect via `&` — then the substring behavior is what you want, and this
  is a safe finding to dismiss for that line.
- If the term you're checking has no known overlapping terms in the
  vocabulary genolint knows about, GL004 won't flag it in the first place
  (this rule is deliberately conservative and only flags known
  substring-collision cases rather than guessing at every `has` call).
