# GL001 — Output extension doesn't match `-O`/output-type

## What it catches

`bcftools` lets you set the output format independently of the output
filename via `-O`/`--output-type` (`b` = compressed BCF, `u` = uncompressed
BCF, `z` = compressed VCF, `v` = uncompressed VCF). Nothing stops you from
writing `-Ov` while naming the file `out.vcf.gz`, or `-Oz` while naming it
`out.vcf`. bcftools does not compress or decompress the file to match the
name — it writes exactly the format you told it to with `-O`, and the
filename is just a string.

GL001 flags a command where the output file's extension implies one
format but `-O`/`--output-type` specifies another:

```bash
# BAD: -Ov (uncompressed VCF) written to a .vcf.gz path
bcftools view -Ov -o out.vcf.gz input.bcf
```

The result is a file named `.vcf.gz` that is actually plain uncompressed
VCF text. Nothing errors at write time — the breakage shows up later, when
something else in the pipeline (`tabix`, `bcftools index`, a Python
`gzip.open`, a Snakemake rule that expects a real bgzipped file) chokes on
a file whose contents don't match its name.

## Why it matters

This is a "silent until downstream" bug — exactly the class of error a
linter is good at catching and a human reviewer tends to miss, because the
command runs successfully and produces a file. It typically surfaces much
later, often in someone else's hands (a collaborator, a CI job, a
reviewer), which makes it expensive to debug back to the source.

## The fix

Make the `-O`/`--output-type` value and the output extension agree:

```bash
# GOOD: -Oz (compressed VCF) written to a .vcf.gz path
bcftools view -Oz -o out.vcf.gz input.bcf

# GOOD: -Ob (compressed BCF) written to a .bcf path
bcftools view -Ob -o out.bcf input.bcf
```

If you deliberately want an uncompressed file, give it an extension that
says so (`.vcf`, not `.vcf.gz`).

## When to ignore it

- If the "extension" genolint is reading isn't actually a bcftools output
  format indicator — e.g. a filename with an unrelated `.gz` from some
  other convention in your pipeline that isn't produced by this bcftools
  call itself (rare, but possible in multi-stage renaming scripts).
- If `-o`/output path is computed dynamically (a shell variable) rather
  than a literal string GL001 can inspect; in that case genolint has
  nothing to check and won't flag anything either way, so there's no
  finding to ignore — just no signal.
